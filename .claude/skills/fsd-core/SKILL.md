# Feature-Sliced Design

## Введение

это методология организации фронтенд-кода, направленная на улучшение масштабируемости, поддерживаемости и предсказуемости проектов. Основные принципы FSD включают разделение кода на слои, слайсы и сегменты, а также строгие правила импорта и определения публичных API

## Структура слоёв

Код организуется в 7 слоёв расположенных от наибольшей ответственности и зависимости к наименьшей:

App — глобальные настройки приложения, провайдеры, роутинг
Processes — устаревший слой, не рекомендуется к использованию
Pages — композиционный слой, страницы приложения с конкретным UI, маршрутами и контейнерами
Widgets — композиционный слой, самостоятельные блоки интерфейса, состоящие из нескольких компонентов и логики собираемых из элементов из нижних слоев
Features — отдельные пользовательские функции (например, кнопка удаления, добавление товара в корзину)
Entities — модули с описанием и логикой сущностей предметной области (например, User, Product, Order)
Shared — общие библиотеки, утилиты, переиспользуемые компоненты

- в проекте не обязательно должны быть все слои,но быть должны как минимум слои Shared, Pages и App.

## Организация директорий

### Слои как директории

слои это папки с названиями в нижнем регистре

```
src/app/          # Слой App
src/pages/        # Слой Pages
src/widgets/      # Слой Widgets
src/features/     # Слой Features
src/entities/     # Слой Entities
src/shared/       # Слой Shared
```

- добавление новых слоев не рекомендуется, их перечень стандартизирован

### Слайсы

Слои (кроме `app` и `shared`) делятся на слайсы — высокосвязанные группы модулей, объединённые по бизнес-домену.

Пример структуры со слайсами:

```
src/pages/access-token/ - слайс access-token
src/pages/account/ - слайс account
src/pages/setting/ - слайс setting
src/features/application/ - слайс application
src/entities/account/ - слайс account
src/entities/user/ - слайс user
```

Правила именования слайсов:
- Имена слайсов должны быть в нижнем регистре (kebab-case)
- Имена определяются предметной областью приложения
- Слои `app` и `shared` не содержат слайсов

### Сегменты

Слайсы и слои app и shared могут содержать сегменты — группы файлов, объединённых по функциональному назначению.

Стандартные сегменты:

- `ui/` — компоненты пользовательского интерфейса
- `model/` — управление состоянием, бизнес-логика, типизация
- `api/` — функции для работы с API
- `lib/` — вспомогательные библиотеки и утилиты
- `config/` — конфигурационные файлы и константы

Пример структуры слайса с сегментами:

```
src/features/authentication/ui/LoginForm.tsx
src/features/authentication/ui/index.ts
src/features/authentication/model/useAuth.ts
src/features/authentication/model/index.ts
src/features/authentication/api/authApi.ts
src/features/authentication/api/index.ts
src/features/authentication/lib/validators.ts
src/features/authentication/lib/index.ts
src/features/index.ts  - public api слайса
```

Правила именования сегментов:
- Названия сегментов описывают их назначение, а не техническую реализацию
- Используйте `ui` вместо `components`
- Используйте `lib` вместо `utils` или `helpers`

## Правило импорта слоёв

Основное правило - Модуль (файл) в слайсе может импортировать другие слайсы только если они находятся на слоях строго ниже.

### Иерархия импортов

App - может импортировать все слои
Pages - может импортировать только нижележащие
Widgets - может импортировать только нижележащие
Features - может импортировать только нижележащие
Entities - может импортировать только нижележащие
Shared


### Примеры допустимых импортов

```typescript
// ✅ features/user-profile/ui/Profile.tsx
import { getUser } from '@/entities/user/api';        // Entities ниже Features
import { Button } from '@/shared/ui/button';          // Shared ниже Features

// ✅ pages/account/ui/Account.tsx
import { UserCard } from '@/entities/user/ui';        // Entities ниже Pages
import { useAuth } from '@/features/authentication';  // Features ниже Pages
import { Button } from '@/shared/ui/button';         // Shared ниже Pages
```

### Примеры недопустимых импортов

```typescript
// ❌ features/user-profile/ui/Profile.tsx
import { LoginForm } from '@/features/authentication'; // Features не может импортировать Features
import { AccountPage } from '@/pages/account';        // Pages выше Features

// ❌ entities/user/api/getUser.ts
import { useAuth } from '@/features/authentication';   // Features выше Entities
```

### Исключения

Слои App и Shared являются исключениями из правила импорта:
- Они могут свободно импортировать друг друга
- Они могут импортировать модули из любых других слоёв
- Это связано с тем, что `app` и `shared` одновременно являются и слоем, и слайсом

```typescript
// ✅ app/Routes.tsx
import { AccountPage } from '@/pages/account';        // Любой слой
import { Button } from '@/shared/ui/button';          // Shared

// ✅ shared/lib/validators.ts
import { ROUTES } from '@/app/config';                // App
import { formatDate } from '@/shared/lib/date';       // Другой сегмент Shared
```

### Вложенность компонентов

Допускается вложение страниц, фич и сущностей друг в друга, но это вложение должно происходить в более высоких композиционных слоях. Например:

- Внутри виджета можно импортировать обе фичи, а затем вставить одну фичу в другую через пропсы или вложение
- Однако одна фича не может импортировать другую фичу напрямую, так как это запрещено правилом импортов для слоёв

## Публичный API

Каждый слайс или сегмент имеет Public API, экспортируя только то, что предназначено для использования вне этого модуля.

### Реализация через index.ts

Public API реализуется с помощью индексных файлов index.ts, которые реэкспортируют необходимые сущности.

Пример Public API слайса:

```typescript
// features/authentication/index.ts
export { LoginForm } from './ui/LoginForm';
export { useAuth } from './model/useAuth';
export { authApi } from './api/authApi';
```

Пример Public API сегмента:

```typescript
// entities/account/api/index.ts
export { useGetUserObjects } from './useGetUserObjects';
export type { UserObject } from './types';
```

### Правила публичного API

1. Все импорты из слайса должны идти через его публичный API
   ```typescript
   // Правильно
   import { LoginForm } from '@/features/authentication';
   
   // Неправильно (прямой импорт из внутренней структуры)
   import { LoginForm } from '@/features/authentication/ui/LoginForm';
   ```

2. Внутри слайса можно использовать прямые импорты
   ```typescript   
   // features/authentication/ui/LoginForm.tsx
   import { useAuth } from '../model/useAuth';
   ```

3. Избегайте циклических зависимостей

## Семантика слоёв

### Shared

Этот слой формирует фундамент для остальной части приложения. Это место для:
- Связей с внешним миром (бэкенды, сторонние библиотеки, environment)
- Собственных библиотек, сконцентрированных на конкретной задаче
- UI-кита приложения (компоненты без бизнес-логики)

Сегменты в Shared:
- `api/` — API-клиент и функции для выполнения запросов к эндпоинтам
- `ui/` — UI-кит приложения (компоненты не должны содержать бизнес-логику)
- `lib/` — коллекция внутренних библиотек (каждая библиотека должна иметь одну область фокуса)
- `config/` — конфигурационные файлы

### Entities

Сущности описывают бизнес-сущности предметной области. Это то, о чём ваше приложение.

Примеры сущностей:
- User (пользователь)
- Product (товар)
- Order (заказ)
- Account (аккаунт)

Сегменты в Entities:
- `ui/` — компоненты для отображения сущности
- `model/` — бизнес-логика и состояние сущности
- `api/` — запросы к API, связанные с сущностью
- `lib/` — утилиты для работы с сущностью

### Features

Фичи реализуют действия, которые пользователь может совершить в приложении.

Примеры фич:
- Кнопка лайка
- Добавление товара в корзину
- Комментирование (если используется в нескольких местах)

Сегменты в Features:
- `ui/` — UI для выполнения действия (например, форма или кнопка выполняющая действие)
- `api/` — вызовы API, необходимые для выполнения действия
- `model/` — валидация, внутреннее состояние, сторы
- `config/` — фиче-флаги и конфигурация

### Widgets

Виджеты:
- это большие самодостаточные блоки интерфейса
- может использоваться как композиционный слой чтобы соединить несколько более мелких компонентов
- eсли блок интерфейса составляет большую часть интересного контента на странице и никогда не используется повторно, он не должен быть виджетом, и вместо этого его следует разместить непосредственно на этой странице.

### Pages

Страницы — это то, из чего состоят веб-сайты и приложения. Одна страница обычно соответствует одному слайсу, но не всегда.

Сегменты в Pages:
- `ui/` — интерфейс страницы, состояния загрузки и границы ошибок
- `api/` — запросы на получение и изменение данных
- `model/` — валидация, внутреннее состояние, сторы, модели сущностей
- `config/` — фиче-флаги и конфигурация

Правило: Нет никаких ограничений на количество кода, которое можно разместить в слайсе страницы, по крайней мере, до тех пор, пока вашей команде не станет сложно ориентироваться в ней.

### App

Всё, что касается приложения целиком, как в техническом смысле (например, провайдеры контекста), так и в бизнес-смысле (например, аналитика).

Сегменты в App:
- `routes/` — конфигурация роутера
- `store/` — глобальная конфигурация хранилища
- `styles/` — глобальные стили
- `entrypoint/` — точка входа в код приложения

Сегменты и наполнение этого слоя в целом допустимо по свободным правилам.


### Еще правила

- наполнение сегментов свободное и определяется командой разработки, допустимо в сегментах организовывать еще внутреннюю структуру папок и файлов при разрастании сегмента
- если количество слайсов растет то можно ввести подслайсы {layer}/{slice}/{subslice}/{segment}
- c 2.1 версии используется page-first подход, если компонент используется один раз только на конкретной странице то он и остается на уровне страницы конкретного слайса, на нижний слой спускается только если переиспользуется разными страницами из разных слайсов
- слайсы должны иметь единообразие в наименовани с точки зрения множественного числа (users, tokens, posts или user, token, post)
- на уровне слоев widgets, pages, features, entites, shared не должно быть index.ts файлов
- имена слайсов не должны совпадать с именами сегментов слоя shared и с другими стандартизированными названиями сегментов (ui, lib, api, config, model)
- количество слайсов не должно быть больше 20, это значит что излишняя декомпозиция в проекте, либо требуется введение подслайсов для группировки слайсов по назначению
- подпапки в сегментах не должны иметь имена, совпадающие с названиями сегментов
- в слое app не должно быть сегмента ui
- кастомные папки сегментов рекомендуется именовать по назначению, а не по реализации (например, создание папки hook ведет к тому что в ней будут лежать хуки и для UI и для получения данных что приведет к засорению этой директории и к усложнению поиска нужных команде хуков)
- в shared/lib допускается не более 15 модулей, если превышает их число - то группировать их по папкам в этой же директории
