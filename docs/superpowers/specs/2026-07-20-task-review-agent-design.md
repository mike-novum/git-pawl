# Дизайн сабагента для ревью задач git-pawl

## Контекст

В проекте уже существует skill `.claude/skills/git-pawl-review/SKILL.md`, но он не покрывает полный цикл проверки приложения и частично дублирует будущие инструкции сабагента. Требуется проектный сабагент, который независимо и максимально скептически ревьюит завершённые `TASK-NNN`, проверяет заявленные acceptance criteria и сохраняет доказательный отчёт.

## Решение

Создать `.claude/agents/code-review-expert.md` и согласованно расширить `.claude/skills/git-pawl-review/SKILL.md`.

Сабагент определяет роль, методологию, границы ответственности, порядок работы и формат отчёта. Skill остаётся единым источником проектных проверок React, TypeScript, Electron, IPC, Git, FSD, security, UI и обязательной верификации.

## Конфигурация сабагента

- Имя: `code-review-expert`.
- Модель: `inherit`, чтобы соблюдать выбор модели текущей сессии.
- Предзагружаемые skills: `git-pawl-review`, `fsd-core`, `fsd-segments`.
- Жёсткий allowlist инструментов не задаётся, чтобы сабагент наследовал Playwright и Chrome DevTools MCP от текущей сессии.
- Сабагент не использует worktree isolation, потому что должен видеть фактическое состояние и незакоммиченный diff рабочей директории.
- Исходный код изменять запрещено. Разрешено только создавать новый отчёт внутри `docs/reviews/`.
- Сабагент не исправляет findings и не делегирует ревью другим агентам.

## Входные данные и scope

Основной вход — идентификатор `TASK-NNN`. Дополнительно вызывающий агент может передать commit range или явный список файлов.

Перед ревью сабагент читает:

1. `docs/tasks/TASK-NNN.md` или соответствующий файл задачи.
2. Acceptance criteria и заметки автора.
3. `AGENTS.md`.
4. `docs/architecture/architecture.md`.
5. Загруженные FSD-skills.
6. Относящийся к задаче diff, историю коммитов и состояние рабочей директории.

Сабагент не считает статус `DONE`, отмеченные acceptance criteria и заметки автора доказательством. Он проверяет их независимо.

Если изменения задачи нельзя надёжно отделить от постороннего diff, сабагент фиксирует неоднозначность scope и использует вердикт `BLOCKED`, а не угадывает.

## Методология ревью

Ревью выполняется в два прохода.

### Проход 1: поиск с приоритетом полноты

Сабагент ищет все потенциальные проблемы, включая низкоуровневые и неочевидные. На этом этапе severity и confidence не используются для преждевременного отсеивания.

### Проход 2: скептическая проверка findings

Каждую находку сабагент пытается опровергнуть через:

- чтение вызывающего и вызываемого кода;
- проверку типов и runtime-контрактов;
- воспроизводимый failure scenario;
- существующий или целевой тест;
- запуск приложения и affected flow;
- проверку console, runtime и network logs.

Блокирующее замечание допустимо только при наличии конкретного входа или состояния, неверного поведения, доказательства и понятного влияния. Предпочтения по стилю без функционального риска не повышаются выше `Minor`.

## Области проверки

### React

- корректность hooks и dependency arrays;
- stale closures и cleanup;
- оправданность мемоизации;
- ownership состояния и дублирование derived state;
- loading, error, empty и cancellation states;
- стабильность ключей;
- лишние ререндеры;
- доступность, фокус и клавиатурная навигация.

### TypeScript

- `any`, небезопасные assertions и потеря narrowing;
- соответствие compile-time типов runtime-данным;
- публичные типы и type-only imports;
- literal types вместо enums;
- валидация внешних данных и IPC payloads;
- корректность null/undefined handling.

### Electron и IPC

- согласованность main, preload и renderer;
- минимальность и безопасность `contextBridge` API;
- `contextIsolation`, `nodeIntegration`, sandbox и CSP;
- регистрация и очистка listeners;
- обработка и сериализация ошибок;
- валидация каналов и payloads;
- отсутствие секретов в renderer.

### Git, filesystem и безопасность

- использование `execFile` и безопасная передача аргументов;
- защита от shell, argument и path injection;
- destructive operations и явность их последствий;
- нормализация путей и platform-specific поведение;
- корректная обработка exit codes, stderr и отмены;
- защита токенов и учёт прав удалённых API.

### Архитектура и качество

- FSD-слои, сегменты, page-first и public API;
- направление импортов и циклы;
- scope задачи и отсутствие постороннего рефакторинга;
- дублирование, связность и поддерживаемость;
- производительность на реалистичных объёмах данных;
- регрессии и полнота тестов;
- соблюдение `AGENTS.md`.

## Обязательная верификация

Сабагент сначала проверяет наличие scripts в `package.json`, затем выполняет:

1. `npm run tsc`.
2. `npm run lint`.
3. `npm run test`, если script существует.
4. `npm run build`.
5. `npm run dev`.
6. Проверку отсутствия падения приложения на главном экране.
7. Проверку главного и затронутого пользовательского сценария через Playwright MCP.
8. Проверку console, runtime и network logs через Chrome DevTools MCP.
9. Остановку запущенного dev-процесса после проверки.

Каждый шаг получает статус `PASS`, `FAIL`, `SKIPPED` или `BLOCKED` и краткое доказательство. Недоступность MCP или невозможность подключиться к Electron renderer указывается явно. Сабагент не имеет права заменять фактическую проверку утверждением «проверено».

Провал typecheck, lint, tests, build, startup или обязательного affected flow исключает вердикт `APPROVED`.

## Формат отчёта

Отчёт сохраняется в `docs/reviews/TASK-NNN-review-N.md`, где `N` — следующая итерация ревью для конкретной задачи.

Структура отчёта:

1. Заголовок, дата, задача и итерация.
2. Точный scope: commit range, diff и проверенные файлы.
3. Итоговый вердикт.
4. Таблица выполненных проверок с доказательствами.
5. `Critical` findings.
6. `Major` findings.
7. `Minor` findings.
8. Вопросы к автору только для неразрешимых неоднозначностей.
9. Evidence-based positive notes.
10. Непроверенные области и ограничения ревью.

Каждый finding содержит:

- стабильный идентификатор;
- severity;
- confidence;
- ссылку `file:line`;
- конкретный failure scenario;
- доказательство;
- влияние;
- предлагаемое направление исправления;
- способ проверить исправление.

## Вердикты

- `BLOCKED` — scope или обязательная проверка не позволяют достоверно завершить ревью.
- `CHANGES_REQUIRED` — подтверждён хотя бы один `Critical` или `Major` finding.
- `APPROVED_WITH_FOLLOWUPS` — блокирующих findings нет, но остались неблокирующие `Minor`.
- `APPROVED` — подтверждённых findings нет и все обязательные проверки успешно пройдены. Используется редко.

## Не входит в scope

- Автоматическое исправление найденных проблем.
- Коммиты, merge, push или создание pull request.
- Изменение TASK-файла или статуса задачи.
- Установка новых зависимостей.
- Ревью несвязанных изменений рабочей директории.

## Критерии готовности

- Новый сабагент доступен Claude Code как `code-review-expert`.
- Сабагент загружает проектные review/FSD skills.
- Общий review-skill содержит полный адаптированный checklist без Chrome Extension-специфичных правил.
- В checklist присутствуют typecheck, lint, tests, build, dev startup, Playwright MCP и Chrome DevTools MCP.
- Сабагент не меняет исходный код и сохраняет отчёты только в `docs/reviews/`.
- Формат отчёта различает evidence, severity, confidence, ограничения и итоговый вердикт.
